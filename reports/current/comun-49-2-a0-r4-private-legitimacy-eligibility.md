# COMUN 49.2-A0-R4 — private legitimacy and eligibility

State: **functional R4 under review; no Production schema or business write in this slice**.

## Objective

R4 separates three questions that must not collapse into publication:

1. whether the declared entity is supported by review evidence;
2. whether the claimed representation is supported by review evidence;
3. whether the private R3 candidate is eligible only for a later projection review.

The derived terminal state in this slice is
`eligible_for_projection_review`. It is not a publication state, does not
verify the R2 representation row, does not create a public projection and does
not open any map.

## Migration

The migration filename was generated by `supabase migration new` using the
repository's pinned Supabase CLI pattern:

`20260925014131_comun_relata_collective_entity_legitimacy_eligibility.sql`.

R4 creates one private append-only table:

`private.comun_relata_collective_entity_candidate_reviews`.

Each review snapshots the active reviewer profile, auth user and reviewer role
privately so a later permission change cannot rewrite historical authority.

A review has exactly two stages:

- `entity_existence`;
- `representation_legitimacy`.

Allowed decisions are:

- `supported`;
- `needs_evidence`;
- `contested`;
- `unsupported`.

Eligibility is derived from the latest decision in each stage plus the live R3
candidate/source invariants. It is never written into the R3 candidate.

Derived eligibility states:

- `pending_review`;
- `needs_evidence`;
- `contested`;
- `blocked`;
- `needs_independent_review`;
- `eligible_for_projection_review`;
- `invalidated`.

## Reviewer authority

Reviewer identity is never accepted from browser input. The server obtains the
authenticated user and passes it only internally to a service-role bridge.

The database independently requires both an active canonical
`comun_admin_users` access row and an active `comun_admin_profiles` profile
with role:

- `admin`;
- `editor`;
- `factual_reviewer`.

`viewer`, `editorial_reviewer`, `publisher` and users without an allowed
active profile fail closed.

A reviewer cannot review a candidate whose source representation belongs to
the same auth user. Self-review is rejected by the database even if that user
also has a reviewer profile.

The two supported stages must also come from distinct reviewer profiles before
the candidate becomes `eligible_for_projection_review`. If the same reviewer
supports both stages, the derived result is `needs_independent_review`.
This is a legitimacy safeguard, not a publication approval.

## Evidence boundary

Review evidence remains private. R4 records a structured basis kind and an
optional/required private reference according to decision shape.

Supported decisions require a non-conflicting basis and private reference.
Needs-evidence uses `insufficient_or_conflicting`. Contested decisions require
a private conflict reference.

The owner DTO never returns reviewer identity or evidence reference.

The reviewer queue exposes only the sanitized R3 snapshot and derived states;
it does not return owner identity, representation/consent IDs or private
review evidence.

## Append-only and contestability

Reviews cannot be updated or deleted. A later review is a new append-only
record, preserving earlier decisions. Current state is derived from the latest
review for each stage.

This permits a later independent correction without destroying the history.
R4 does not introduce a public accusation, public verification badge or public
rejection label.

## Zero propagation

R4 does not:

- modify the R3 candidate snapshot;
- promote a representation to `verified`;
- create a public table/view;
- create a public projection;
- modify `future_map_eligibility`;
- open the map;
- index Search;
- create a Pauta, Ação or Comunidade;
- connect collective entities to collective report cases;
- publish reviewer evidence.

The existing helpers explicitly keep legitimacy review and
`eligible_for_projection_review` insufficient for publication or public-map
authority.

## Runtime surfaces

Owner-only:

`comun_relata_collective_entity_server_candidate_legitimacy_list_own`.

Reviewer-only:

`comun_relata_collective_entity_server_candidate_review_queue`;

`comun_relata_collective_entity_server_candidate_review`.

All three are server-only `SECURITY DEFINER` bridges with
`search_path=pg_catalog`, postgres ownership and service-role-only EXECUTE.

The review table has RLS/FORCE RLS and no direct grants to PUBLIC, anon,
authenticated or service_role.

## Disposable proof

The R4 disposable proof starts from the full R1 + R2 + R3 local schema and
creates only local Auth/test data.

It proves:

- initial candidate state is pending/pending/pending_review;
- owner B cannot see owner A's candidate;
- allowed reviewer sees the sanitized queue;
- owner cannot self-review even with a factual-reviewer profile;
- viewer role cannot review;
- request replay is idempotent;
- conflicting request replay blocks;
- review UPDATE/DELETE block;
- the same reviewer supporting both stages => needs_independent_review;
- existence supported + representation needs evidence => needs_evidence;
- later supported representation review => eligible_for_projection_review;
- the R3 candidate remains pending_legitimacy;
- contested review dominates to contested;
- source revocation invalidates the candidate and derived eligibility;
- invalidated candidate cannot receive new reviews;
- anon/authenticated cannot invoke R4 bridges directly;
- zero canonical security findings.

## Production boundary

This R4 development slice must not apply the migration in Production and must
not create any Production review row.

The next release preparation, if R4 is accepted and merged, remains a separate
gate. R5/public projection is not part of R4.
